\textit{Program analysis}

Given a program $P$, try to find whether some property
holds for all its behaviours.

\[
P \models \phi
\]

eg. want to check

\[
P \models \text{``no divide by zero''}
\]

Two broad ways:

\[
\text{static} \qquad\qquad \text{dynamic}
\]

static $\rightarrow$ don't run program

\begin{itemize}[leftmargin=18pt,itemsep=1pt]
    \item compiler analysis
    \item data-flow analysis
    \item abstract interpretation
    \item symbolic execution
    \item model checking
\end{itemize}

dynamic $\rightarrow$ observe program while running

\begin{itemize}[leftmargin=18pt,itemsep=1pt]
    \item testing
    \item profiling
    \item runtime monitoring
    \item dynamic taint analysis
\end{itemize}

\vspace{5pt}

\textit{Formal verification}

FV = model + specification + proof

model $\rightarrow$ semantics of program

specification $\rightarrow$ property we want to be correct

proof $\rightarrow$ show that program satisfies specification
under the given semantics.

examples:
model checking, theorem proving, symbolic verification

\vspace{5pt}

\textit{PA vs FV}

Program analysis can tell us things about the program, e.g.

\begin{itemize}[leftmargin=18pt,itemsep=1pt]
    \item amount affects balance
    \item there are 2 possible paths
    \item no pointer dereference
\end{itemize}

But FV starts with a property and actually proves it.

For example,

\[
balance \geq 0 \ \land\ amount \geq 0
\Rightarrow balance' \geq 0
\]

so idea is not just ``seems true'' but prove it.

\vspace{5pt}

\textit{Why is this hard?}

Think of Rice's theorem.

Main issue:

\[
\text{precision} \longleftrightarrow \text{scalability}
\]

more precision $\Rightarrow$ usually more computation/cost.

Also:

\begin{itemize}[leftmargin=18pt,itemsep=1pt]
    \item infinitely many possible inputs
    \item number of paths can become exponential
    \item loops $\rightarrow$ potentially infinitely many executions
\end{itemize}

Real programs have complicated state too:

pointers, heap objects, data structures, recursion,
callbacks, exceptions, threads, files, network etc.

So exact analysis becomes difficult very quickly.

\vspace{5pt}

\textit{where can LLMs help?}

LLMs can generate possible specifications from natural language.

Natural language $\rightarrow$ logic

Example:

``every accepted request eventually gets a response''

\[
G(req) \rightarrow F(resp)
\]

They can also help with semantic inference:

\begin{itemize}[leftmargin=18pt,itemsep=1pt]
    \item invariants
    \item preconditions
    \item postconditions
    \item auxiliary lemmas
\end{itemize}

Sometimes the invariant is actually something the
decision procedure needs, but the SMT solver cannot
find it by itself.

LLM is good at generating candidate invariants/lemmas,
but candidates still need to be checked.

\vspace{5pt}

\textit{limitations of LLMs}

LLMs cannot reliably verify their own output.

So output of LLM $\neq$ proof by itself.

Not sound / complete.

soundness:
no false positives

completeness:
no false negatives

Also weaker for very precise reasoning.

For example,

\[
\forall x\exists y\; R(x,y)
\]

may be handled correctly in one step but the quantifiers
can accidentally get interchanged later.

\vspace{5pt}

\textit{overall idea}

LLMs can help at different layers:

\begin{itemize}[leftmargin=18pt,itemsep=2pt]
    \item property discovery
    $\rightarrow$ what should be checked?
    
    \item abstraction discovery
    $\rightarrow$ what information should analyzer keep?
    
    \item proof search
    $\rightarrow$ which invariant/lemma helps?
    
    \item tool orchestration
    $\rightarrow$ which analyzer / verifier / solver to use?
\end{itemize}

main idea:

\[
\boxed{\text{trust but verify}}
\]
